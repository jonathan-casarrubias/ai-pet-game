# AI–Game Core Generative Contract

This document defines the conceptual boundary between Game Core and AI for generating gameplay. It elaborates how the Game Core supplies controlled information, how AI proposes concrete gameplay within the generative capability space, and how Game Core validates what may become usable gameplay. It does not replace or redefine the approved architectural decisions or introduce an implementation contract.

The central principle is:

> Game Core defines the space of valid gameplay. AI generates concrete gameplay within that space. Game Core decides what is valid and authoritative.

This is a conceptual design document. It does not define concrete interfaces, schemas, APIs, prompts, models, providers, frameworks, serialization formats, validation algorithms, persistence structures, or UI behavior.

## Contract Purpose

The Game Core–AI boundary exists to give AI enough relevant information to generate meaningful gameplay without making AI a second game engine or exposing the internal Game Core without control.

The contract provides a deliberate separation between:

- the authoritative rules, state, capabilities, and safety boundaries defined by Game Core;
- the controlled information selected for a particular generation purpose; and
- the untrusted gameplay proposal generated by AI.

The conceptual relationship is:

```text
Game Core
    ↓
Controlled Generation Context
    ↓
AI
    ↓
Generated Gameplay Proposal
    ↓
Game Core Validation
    ↓
Accepted Gameplay Context
```

Neither information crossing the boundary nor an AI response becomes authoritative merely because it crosses the boundary. The controlled context represents information whose authority remains in Game Core. A generated proposal remains untrusted until Game Core evaluates it. Only Game Core can accept a usable gameplay context or establish an authoritative state transition.

This boundary supports data minimization, provider and model replacement, independently testable validation, and deterministic Game Core authority wherever practical. It also prevents an unrestricted chatbot or an AI-controlled rules engine from becoming the product architecture.

## Controlled Generation Context

A **Controlled Generation Context** is the deliberately selected representation of relevant information that Game Core makes available to AI for a specific generation purpose. It is not unrestricted access to Game Core, its database, or its complete internal state.

The context may conceptually include the following categories.

### Relevant authoritative state

Game Core may provide the subset of current state needed for the generation request, such as relevant player or game state, the current world situation, relevant authoritative existing entities and relationships, current progression boundaries, and the current gameplay context when one exists.

The supplied representation informs generation but does not transfer authority to AI. Game Core remains the source of truth for the facts represented in the context and for any facts not included in it.

### Relevant entity and contextual-element space

The context may distinguish authoritative existing entities from categories of contextual elements that AI is permitted to generate for the current situation. A generated element may be novel and need not have existed previously, but Game Core must define the supported category, relevant properties, relationships, capabilities, contextual relevance, constraints, and safety boundaries that govern it.

The context does not grant AI authority to create persistent entities. A generated contextual element remains context-scoped unless an accepted Game Core transition establishes it as authoritative state.

### Relevant capability space

The context may identify capabilities that are available and relevant to the current situation, together with the applicable rules, constraints, and safety boundaries needed to keep generation within the valid generative space. The relevant capability space may be contextual and player-specific; age or developmental band, progression, gameplay history, discoveries, curiosity patterns, game-domain personality, preferred interaction complexity, previous outcomes, and current world situation may influence which capabilities, entity categories, properties, interactions, and complexity levels are currently available to generation.

AI may use this information to compose gameplay, but it does not receive authority to redefine capability meaning, applicability, or effects.

### Structured gameplay history

The context may include structured game-domain history relevant to the generation purpose, such as previous accepted actions, meaningful outcomes, discoveries, recent experiences, gameplay-demonstrated preferences, progression history, and game-domain personality state.

Raw conversation history is not the default source of memory. The information provided should be relevant to gameplay and proportionate to the current generation need.

### Generation purpose

Generation is purposeful rather than an unrestricted request for something entertaining. The purpose may be to create an initial gameplay context, continue or transform an existing context, respond to a meaningful accepted action, generate a new context after completion, or create a context around a newly relevant capability.

These are conceptual examples, not an exhaustive set of generation modes. The important boundary is that Game Core determines why generation is being requested and supplies context relevant to that purpose.

### Safety and domain boundaries

The context may include target-age requirements, applicable safety requirements, capability restrictions, progression boundaries, contextual exclusions, and world constraints. These are authoritative boundaries, not suggestions for AI to reinterpret or relax.

## Information Not Provided as Authority

The Controlled Generation Context must not imply that AI receives:

- unrestricted access to Game Core or its internal implementation;
- direct database access or arbitrary querying of persistent state;
- unrestricted raw chat history;
- unnecessary personal or sensitive child information;
- secrets, credentials, or other security-sensitive information;
- unrestricted external information;
- direct mutation capabilities;
- authority to invoke game actions;
- authority to modify rules or constraints; or
- authority to create new fundamental capabilities.

AI receives a deliberate representation of relevant information, not the Game Core itself. It may generate a proposal from that representation, but it cannot use the boundary to bypass Game Core validation or acquire a second path to authoritative state.

## Generated Gameplay Proposal

A **Generated Gameplay Proposal** is the untrusted gameplay context proposed by AI in response to a Controlled Generation Context. It is a candidate for validation, not an authoritative result.

Conceptually, a proposal may describe:

- the current gameplay situation;
- relevant authoritative entities, generated contextual elements, and their contextual relationships;
- a composition of available and applicable capabilities;
- contextual interaction possibilities;
- narrative or descriptive framing;
- contextual constraints that should be respected;
- categories of actions a player might attempt;
- possible categories of consequences; and
- contextual conditions under which the situation might continue or be complete.

The proposal gives shape to a possible gameplay situation. It does not establish authoritative facts, accept player behavior, execute capabilities, or determine consequences. Any claim in the proposal remains untrusted until it is independently validated or established by Game Core.

AI may propose a novel contextual element, such as an object, creature, environmental element, phenomenon, or artifact, when it belongs to a Game Core-supported category and is relevant to the current context. The proposal does not establish that the element exists authoritatively or persistently. Game Core independently determines whether the element may be used in the context and whether a later accepted transition establishes it as discovered or persistent.

AI does not generate or establish:

- authoritative facts or state;
- rules or invariants;
- new fundamental capabilities;
- accepted player actions;
- rewards or progression;
- authoritative discoveries;
- authoritative personality changes;
- authoritative game memory; or
- final consequences.

If such matters are mentioned as part of a proposal, they are descriptions or suggestions until Game Core establishes them through an authoritative transition.

## Proposal and Authoritative Result

The authority boundary is:

```text
AI Proposal
     ↓
Game Core Validation
     ↓
Accepted Gameplay Context
```

An accepted gameplay context means that Game Core has determined the generated context is valid and usable for interaction within the current capability space and authoritative state.

It does not mean that everything stated inside the AI response has become true. In particular, acceptance does not by itself establish narrative descriptions, generated contextual elements, entities, discoveries, possible consequences, player actions, progression, rewards, personality changes, or memory as authoritative facts.

Only an accepted Game Core transition establishes authoritative facts and consequences. The accepted context is therefore a bounded interaction situation, not a new source of truth.

## Capability References

AI may compose capabilities that are available, applicable, relevant to the supplied context, and inside the capability space defined by Game Core. This is composition within a bounded generative space, not selection from a finite catalog of complete experiences.

AI must not:

- invent capabilities;
- redefine capability semantics;
- alter capability constraints or effects;
- introduce unsupported mechanics; or
- assume that a capability exists merely because it sounds plausible.

Game Core remains authoritative over capability definitions, applicability, rules, constraints, and effects. The contract permits AI to generate novel combinations and sequences of supported capabilities, including interactions with valid generated contextual elements, but not to expand the fundamental runtime capabilities of the game or create unsupported authoritative entities.

## Player Actions Are Outside the AI Contract

The AI-generated proposal may describe possible interactions, but the actual player action comes independently from the player and client interaction. Player actions are external inputs to Game Core and are not generated, accepted, or fabricated by AI.

AI must not:

- claim that the player performed an action;
- assume that the player followed a suggested action;
- encode an action as already accepted;
- skip player-action validation; or
- force the next state based on an expected action.

The relationship is:

```text
AI proposes context
        ↓
Player chooses or attempts an action
        ↓
Game Core validates the actual action
```

A player may perform a valid action that was not explicitly anticipated by the proposal. If the action is applicable under the authoritative state and capability boundaries, Game Core evaluates it on its own terms rather than treating the proposal as an exhaustive list of permitted player behavior.

## Consequence Authority

AI may propose possible consequence categories, contextual expectations, or narrative framing for what might happen. AI does not determine which consequence actually occurs.

Game Core independently evaluates the actual player action against authoritative state, capabilities, rules, constraints, invariants, progression boundaries, and safety requirements. Only the resulting accepted Game Core transition determines the actual consequence.

Accordingly, AI cannot decide whether:

- a reward is granted;
- progression occurs;
- a discovery becomes authoritative;
- personality changes;
- memory or an event is recorded; or
- any other authoritative consequence takes place.

The proposal can make gameplay possibilities understandable and coherent, but it cannot turn a possibility into an outcome. Authority remains with Game Core.

## Validation Responsibilities

The contract contains two distinct validation paths.

### AI proposal validation

Application or transport boundaries may perform structural, transport-level, parsing, or basic shape validation and may reject malformed or otherwise unusable input before it reaches the domain. Passing application-level validation does not make a proposal authoritative or semantically valid. Game Core remains the authoritative domain boundary for semantic validation and determines whether the proposal belongs within the generative capability space, including whether its capabilities, applicability, state compatibility, rules, constraints, invariants, progression boundaries, consequences, and safety or domain requirements are valid. An external validation layer may reject invalid input, but it cannot make an otherwise invalid gameplay proposal authoritative. Conceptually, this includes checking:

- structural validity;
- capability validity;
- capability applicability;
- compatibility with current state;
- rule and constraint compliance;
- safety boundaries;
- progression boundaries;
- unsupported mechanics; and
- unsupported consequences.

The question is whether the proposal can validly exist as a gameplay context in the current situation. Game Core does not need to compare it with a previously authored experience because the architecture uses bounded generation, not bounded selection.

### Player action validation

Game Core separately evaluates the actual player action. Conceptually, this includes checking:

- whether the action is recognized;
- whether the action is applicable;
- whether the required capability exists;
- whether current state permits the action;
- whether rules, constraints, and invariants hold; and
- what authoritative transition and consequence result.

These paths must not be merged. An accepted AI proposal does not pre-accept a player action, and a rejected player action does not mean that the generated context itself was invalid.

## Rejection and Correction

When AI produces an invalid proposal, the proposal must not mutate authoritative state or become partially accepted as authoritative gameplay. Conceptually, the correction flow is:

```text
AI Proposal
    ↓
Validation
    ↓
Invalid
    ↓
Structured rejection information
    ↓
Optional bounded correction
    ↓
Revalidation
```

Rejection information should explain the violated boundary sufficiently for AI to address the problem, without transferring generative responsibility to Game Core. Game Core identifies what is invalid; AI remains responsible for proposing a corrected gameplay context.

Correction attempts must be bounded. A correction cannot redefine the capability space, weaken a rule, or cause Game Core to accept invalid gameplay merely to terminate the loop. If valid generation cannot be obtained, a safe fallback path is required, but its implementation is outside this document.

This correction flow is separate from player-action rejection. An invalid AI proposal means that a candidate gameplay context cannot be used. An invalid player action means that the player's attempted action cannot produce the requested transition under the current authoritative state. Neither event grants AI additional authority.

## Generation Purpose and Capability Scope

AI should not receive the entire capability universe for every generation request by default. Game Core or the surrounding application flow should provide the relevant, potentially player-specific capability space for the current purpose.

Conceptually:

```text
Authoritative State
      +
Generation Purpose
      +
Relevant Capability Space
      +
Safety / Domain Constraints
      +
Relevant Structured History
      ↓
Controlled Generation Context
      ↓
AI
```

This preserves relevance, boundedness, data minimization, provider independence, validation efficiency, and separation between Game Core and AI. The method for determining relevance is an implementation concern outside this document; the conceptual requirement is that context is intentional and purpose-specific.

## Context Evolution and Regeneration

The contract supports the broader gameplay loop after a player action:

```text
Player Action
    ↓
Game Core
    ↓
Authoritative State
    ↓
Determine whether current context remains valid
    ↓
Continue / evolve / transform / complete / end
    ↓
Generate new context when appropriate
```

After an accepted action, Game Core determines whether the current context can continue, must evolve or transform, has completed, or should end. If generation is needed, Game Core creates a new Controlled Generation Context from the updated authoritative state and relevant history.

AI does not carry authoritative state from one generation to another. Each generation remains grounded in the current Game Core state and controlled context. This prevents an earlier proposal, an AI assumption, or a stale description from becoming an independent source of truth.

## Novelty Without an Experience Catalog

The contract supports genuinely novel gameplay without requiring a finite list of predefined experiences. Novelty can emerge through:

- new compositions of supported capabilities;
- different orderings of valid capabilities;
- player-specific context;
- valid player actions that were not explicitly anticipated by AI;
- changed authoritative state;
- changed relationships between entities;
- novel context-scoped elements from supported categories;
- prior discoveries and meaningful outcomes; and
- subsequent generation from updated structured history.

The product therefore uses **bounded generation, not bounded selection**. AI is not an experience selector choosing from a catalog, and the contract does not define a catalog of contexts, adventures, quests, branches, or outcomes. Game Core defines what can validly exist; AI proposes what might happen now; player behavior and accepted state transitions influence what can be generated next.

Novelty does not mean that AI may invent arbitrary runtime mechanics or rewrite the rules. It means that concrete gameplay can emerge from valid capability composition, current context, player agency, and state evolution without having been manually authored in advance.

## Determinism and Provider Independence

AI generation may be probabilistic and may produce different valid gameplay contexts across runs or providers. Game Core validation and authoritative transitions must remain deterministic and testable wherever practical.

Different AI providers or models may express different valid contexts, but provider differences must not change the fundamental meaning of Game Core rules, capabilities, invariants, or accepted player actions. Replacing an AI provider must not require redesigning Game Core authority or the generative capability space.

The contract is therefore semantic rather than tied to a particular model, provider, framework, or orchestration technology.

## Security and Child Safety

Child safety and information boundaries apply to both sides of the contract. The system must prevent AI from receiving or requesting unnecessary sensitive child information, secrets, credentials, unrestricted personal data, or unrestricted external information.

Generated proposals must not introduce secrecy, emotional dependency, manipulation, coercion, unsafe real-world instructions, adult content, or unsupported mechanics. They must remain within the applicable age, world, gameplay, progression, and safety boundaries.

Safety constraints are authoritative. AI cannot reinterpret them as optional guidance, and a novel proposal cannot bypass them merely because it is creative or contextually plausible.

## Relationship to Existing Documents

This document clarifies the Game Core–AI boundary without redefining the existing architecture.

- **ADR-001 — Game Core Authority:** Game Core remains the authoritative source of game state, rules, transitions, progression, rewards, and accepted consequences. This contract provides no alternate authority path.
- **ADR-002 — Bounded AI:** AI remains a bounded narrative and creative engine. The contract explains bounded generation as generation within Game Core-defined capabilities, rules, constraints, invariants, progression boundaries, and safety requirements rather than unrestricted creativity or finite experience selection.
- **ADR-006 — AI/Game Core Contract:** The controlled generation context and generated gameplay proposal are the conceptual forms of the controlled, typed, untrusted proposal relationship. The proposal must be validated before it can be used, and it cannot directly mutate authoritative state.
- **ADR-007 — AI-Driven Player Experience:** ADR-007 establishes the product and architectural decision for an AI-driven player experience through bounded generation, not bounded selection. This document explains the boundary through which that generation occurs.
- **`generative-capability-space.md`:** This document uses the generative capability space as the boundary of valid gameplay. It does not replace the definition of that space or turn it into an experience catalog.
- **`capability-model.md`:** Capabilities remain reusable, applicable, and composable building blocks. AI may compose them, while Game Core retains authority over their meaning, applicability, and effects.
- **`generated-sequence-and-player-actions.md`:** A proposal may provide a bounded gameplay context rather than a rigid script or predefined decision tree. Player actions remain independent inputs to Game Core.
- **`generated-gameplay-context-and-state.md`:** An accepted gameplay context is usable for interaction but is not itself a new source of authoritative state. Only Game Core transitions establish facts and consequences.

Together, these documents describe a hierarchy in which Game Core defines and enforces the valid space, AI proposes novel gameplay within that space, and player actions drive authoritative state evolution.

## Explicit Non-Goals

This document does not define:

- TypeScript interfaces;
- JSON schemas or DTOs;
- API contracts or networking;
- prompt templates;
- model or provider selection;
- AI frameworks, agents, or orchestration tools;
- serialization formats;
- validation algorithms;
- retry or correction implementation;
- fallback implementation;
- database or persistence implementation;
- WebSockets;
- UI representation; or
- concrete gameplay mechanics.

It also does not define a gameplay catalog, a finite list of capabilities intended to represent the final product, predefined adventures, predefined quests, manually authored branches, or a library of complete experiences. Those concerns must not be introduced as a hidden substitute for bounded generation.

## Design Principles

- **Game Core defines the valid space; AI generates within it.**
- **Bounded generation, not bounded selection.**
- **A controlled context informs AI without transferring authority.**
- **AI proposals are untrusted until validated.**
- **Accepted context is usable for interaction, not automatically authoritative fact.**
- **Player actions are independent inputs and must be validated separately.**
- **Only accepted Game Core transitions establish consequences.**
- **Novel composition is allowed; unsupported mechanics are not.**
- **Correction enables valid generation but never creates an infinite retry loop.**
- **Provider or model replacement must not redefine Game Core rules.**
- **Safety boundaries remain authoritative regardless of generative novelty.**
